Before you begin

HCP Terraform is HashiCorp's hosted service for running Terraform. It was called Terraform Cloud until 2024, and you will still see that name in older material. Terraform Enterprise is the self-hosted version of the same product. Everything so far used the Terraform CLI on your own computer, which HashiCorp calls Terraform Community Edition.

This whole module maps to objective 8 of the exam. Part 8c (workspaces and projects) was added in version 004.

1

What HCP Terraform does

Remote runs, remote state and the three ways to start a run.

FeatureWhat it gives you
Remote stateState stored, encrypted, versioned and locked for you. No bucket to manage.
Remote operationsPlans and applies run on HCP Terraform's servers, not your laptop. Everyone sees the same run history and logs.
WorkspacesEach workspace holds one configuration's state, variables, settings and run history.
Private registryShare your own modules and providers inside your organisation.
Team accessTeams with permissions per workspace or project.
Policy as codeSentinel or OPA policies checked between plan and apply.

Three workflows

WorkflowHow a run starts
VCS-drivenThe workspace is connected to a Git repository. A merge to the main branch starts a plan and apply; a pull request gets a speculative plan (plan only, cannot be applied) shown on the pull request.
CLI-drivenYou run terraform plan and apply on your computer as usual, but they execute in HCP Terraform and stream the output back.
API-drivenAnother tool, such as a CI pipeline, uploads the configuration and starts runs through the API.

A workspace's execution mode can be Remote (the default: runs happen in HCP Terraform), Local (runs happen on your computer; HCP Terraform only stores state) or Agent (runs happen on agents you host inside your own network).

Connecting the CLI

terraform login, the cloud block, and migrating state.

terraform login     # opens a browser to create an API token, saved in ~/.terraform.d/credentials.tfrc.json

The cloud block

terraform {
  cloud {
    organization = "sf-tf-course-yourname"

    workspaces {
      name    = "tf2-m8-web"         # one named workspace
      project = "Terraform Course"   # optional: the project it belongs to
    }
  }
}
  • The cloud block replaces a backend block. A configuration cannot have both.
  • Use workspaces { tags = [...] } instead of name to work with several workspaces that share tags; then pick one with terraform workspace select.
  • Run terraform init after adding the block. If there is existing state (local or another backend), init offers to migrate it into the workspace.
  • Like backends, the cloud block cannot use variables. The TF_CLOUD_ORGANIZATION and TF_WORKSPACE environment variables can supply values instead.
Exam tip

With remote execution, variables and credentials must be set in the workspace (or a variable set), because the run happens on HCP Terraform's servers. Your local AWS_PROFILE and credentials file are not available there, and -var and -var-file options cannot be used with remote runs.

Organising and governing

Workspaces, projects, variable sets, run triggers, and the governance features.

Workspaces and projects

An organisation contains projects, and each project contains workspaces. A common pattern is one workspace per configuration per environment, such as network-dev, network-prod, app-dev, app-prod, grouped into projects by team or application. Permissions and variable sets can be assigned to a whole project.

These are different from CLI workspaces (terraform workspace new dev), which only keep several state files for one configuration in the same backend.

Variable sets

A variable set is a group of variables (Terraform variables or environment variables) applied to many workspaces, a whole project, or the entire organisation. Typical use: one set of AWS credentials used by every workspace in a project. Variables can be marked sensitive, which makes them write-only in the interface.

Run triggers

A run trigger links workspaces: when a source workspace (for example network) finishes an apply, HCP Terraform queues a run in the connected workspace (for example app). Outputs can be shared between workspaces with the tfe_outputs data source.

Governance and collaboration

FeatureWhat it does
Teams and permissionsControl who can read, plan, apply or administer each workspace or project
Policy enforcementSentinel or OPA policies run after the plan. Advisory, soft-mandatory (can be overridden) or hard-mandatory (blocks the apply)
Private registryPublish modules and providers for use inside the organisation, including no-code modules that others can deploy without writing HCL
Health: drift detection and continuous validationScheduled checks that report drift and failing check blocks, on paid tiers
Dynamic provider credentialsShort-lived cloud credentials through OIDC trust, so no long-lived keys are stored in HCP Terraform
ExplorerSearch and report across all workspaces, for example provider versions or modules in use
Change requestsRecord follow-up work against a workspace, such as an outdated module to update
Run tasksCall outside services, such as security scanners, during a run

Lab: run the web server from HCP Terraform

Create a free organisation, connect the CLI, store AWS credentials in a variable set and run remotely.

1. Organisation, project and credentials

  1. Sign up for a free account at app.terraform.io with your SourceFuse email.
  2. Create an organisation, for example sf-tf-course-yourname.
  3. Create a project called Terraform Course.
  4. Go to Settings → Variable sets → Create variable set. Name it aws-lab-credentials, apply it to the Terraform Course project, and add two environment variables, both marked Sensitive: AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY, with your sandbox keys.

2. The configuration

tf2-lab-m8/main.tf

terraform {
  required_version = ">= 1.12.0"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
  cloud {
    organization = "sf-tf-course-yourname"      # your organisation
    workspaces {
      name    = "tf2-m8-web"
      project = "Terraform Course"
    }
  }
}

provider "aws" {
  region = "us-east-1"
  default_tags { tags = { Project = "tf-course-2", Lab = "m8" } }
}

variable "environment" {
  type    = string
  default = "dev"
}

data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id
  instance_type = "t3.micro"
  tags          = { Name = "tf2-m8-web-${var.environment}" }
}

output "instance_id" {
  value = aws_instance.web.id
}
cd tf2-lab-m8
terraform login          # paste the token when asked
terraform init           # creates the tf2-m8-web workspace in the project
terraform plan           # runs in HCP Terraform; a link to the run is printed
terraform apply

3. Look around

  • Open the workspace in the browser. See the run, its plan and apply logs, and the States tab with the state versions.
  • Under Variables, add a Terraform variable environment = test. Start a new run from the browser with New run. The plan shows the tag change, without using your computer at all.
  • Note that your local folder has no terraform.tfstate: the state is in the workspace.

4. Clean up

terraform destroy        # also runs remotely

Then, in the workspace, go to Settings → Destruction and Deletion and delete the workspace. Delete the variable set too if you no longer need it.

Check your work
  • The plan output printed a link to a run in HCP Terraform
  • The workspace showed state versions and the run history
  • A run started from the browser used the workspace variable environment = test
