Custom Conditions

Stop bad values and broken assumptions early with variable validation, preconditions, postconditions and check blocks.

Before you begin

Terraform already checks types: a string variable will not accept a list. Custom conditions let you add your own rules, with your own error messages, so mistakes are caught during plan instead of halfway through an apply. This topic was added in version 004 of the exam.

1

Variable validation

Reject a bad input value before anything else happens.

A validation block inside a variable has a condition that must be true, and an error_message shown when it is false.

variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "The environment must be dev, test or prod."
  }
}

variable "instance_type" {
  type = string
  validation {
    condition     = can(regex("^t3\\.", var.instance_type))
    error_message = "Use a t3 instance type, for example t3.micro."
  }
}
  • A variable can have several validation blocks; all must pass.
  • The can() function returns false instead of an error when an expression fails, which makes it useful inside conditions.
  • Since Terraform 1.9 a validation condition can also refer to other variables, data sources and locals, not only the variable being checked.
  • If a validation fails, Terraform stops before planning any resources.
terraform plan -var="environment=staging"
# Error: Invalid value for variable
#   The environment must be dev, test or prod.
2

Preconditions and postconditions

Check assumptions just before and just after a resource is handled.

A precondition or postcondition goes inside a lifecycle block. Each has a condition and an error_message.

CheckedCan refer toUse it for
preconditionBefore the object is created, updated or readVariables, other resources, data sources"The AMI I was given must be x86_64"
postconditionAfter the object is created, updated or readThe object itself, through self"The instance must have a public IP"
data "aws_ami" "app" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = [var.ami_name_pattern]
  }
  lifecycle {
    postcondition {
      condition     = self.architecture == "x86_64"
      error_message = "The AMI must be for x86_64. Check ami_name_pattern."
    }
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.app.id
  instance_type = var.instance_type

  lifecycle {
    precondition {
      condition     = data.aws_ami.app.root_device_type == "ebs"
      error_message = "The AMI must use an EBS root volume."
    }
    postcondition {
      condition     = self.public_ip != ""
      error_message = "The web server must have a public IP address."
    }
  }
}

output "web_url" {
  value = "http://${aws_instance.web.public_ip}"
  precondition {
    condition     = aws_instance.web.public_ip != ""
    error_message = "No public IP, so there is no URL to show."
  }
}

Resources and data sources can have both. Outputs can have precondition only. A failed condition is an error: the plan or apply stops.

Exam tip

Validation checks one input when it arrives. Preconditions and postconditions check assumptions about resources and data. Check blocks (next section) report problems without stopping the run.

3

Check blocks

Ongoing checks that warn instead of failing.

A check block sits on its own, outside any resource. It holds one or more assert blocks, and can also hold one scoped data source that only the check can use.

check "website_up" {
  data "http" "site" {
    url = "http://${aws_instance.web.public_ip}"
  }

  assert {
    condition     = data.http.site.status_code == 200
    error_message = "The website did not return HTTP 200."
  }
}
  • Checks run at the end of every plan and apply.
  • A failed assertion is a warning, not an error. The run carries on and the resources are still created or changed.
  • If the scoped data source itself fails (for example, the site is unreachable), that is also reported as a warning.
  • In HCP Terraform, health assessments run check blocks on a schedule, to show when a workspace stops meeting them.
KindWhereWhen it fails
Variable validationInside a variableError, run stops
Precondition / postconditionlifecycle of a resource or data source; output (precondition)Error, run stops
Check blockTop level of a moduleWarning, run continues

Lab: guard rails for the web server

Add validation, conditions and a check to a small web server.

Create a folder tf2-lab-m2. This lab uses the hashicorp/http provider for the check block.

tf2-lab-m2/main.tf

terraform {
  required_version = ">= 1.12.0"
  required_providers {
    aws  = { source = "hashicorp/aws", version = "~> 6.0" }
    http = { source = "hashicorp/http", version = "~> 3.4" }
  }
}

provider "aws" {
  region = "us-east-1"
  default_tags { tags = { Project = "tf-course-2", Lab = "m2" } }
}

variable "environment" {
  type    = string
  default = "dev"
  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "The environment must be dev, test or prod."
  }
}

variable "instance_type" {
  type    = string
  default = "t3.micro"
  validation {
    condition     = can(regex("^t3\\.", var.instance_type))
    error_message = "Use a t3 instance type, for example t3.micro."
  }
}

data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }
  lifecycle {
    postcondition {
      condition     = self.architecture == "x86_64"
      error_message = "The AMI must be for x86_64."
    }
  }
}

resource "aws_security_group" "web" {
  name_prefix = "tf2-m2-web-"
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.al2023.id
  instance_type          = var.instance_type
  vpc_security_group_ids = [aws_security_group.web.id]
  user_data              = <<-EOF
    #!/bin/bash
    dnf install -y httpd
    echo "Hello from ${var.environment}" > /var/www/html/index.html
    systemctl enable --now httpd
  EOF
  tags = { Name = "tf2-m2-web-${var.environment}" }

  lifecycle {
    postcondition {
      condition     = self.public_ip != ""
      error_message = "The web server must have a public IP address."
    }
  }
}

check "website_up" {
  data "http" "site" {
    url = "http://${aws_instance.web.public_ip}"
  }
  assert {
    condition     = data.http.site.status_code == 200
    error_message = "The website did not return HTTP 200."
  }
}

output "web_url" {
  value = "http://${aws_instance.web.public_ip}"
}

This lab uses the default VPC, as in Course 1. Now try each rule:

cd tf2-lab-m2
terraform init
terraform plan -var="environment=staging"     # validation error, run stops
terraform plan -var="instance_type=m5.large"  # validation error, run stops
terraform apply                               # works; the check may warn while the server starts
# wait two minutes, then:
terraform plan                                # the check now passes: no warning
terraform destroy
Check your work

  • The first apply finished even if it showed a website_up warning
  • A plan a few minutes later showed no warning
