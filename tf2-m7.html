Before you begin

Most teams do not start with empty accounts. There are servers, buckets and networks that were created manually long before Terraform arrived. This module shows how to adopt them into Terraform, how to look at and adjust state safely, and how to get more detail when something goes wrong.

1

Importing with import blocks

Adopt an existing resource into Terraform, reviewed through a plan.

Terraform only manages what is in its state. To adopt an existing resource, you need two things: a resource block that describes it, and an import that records it in state. Since Terraform 1.5 the recommended way is an import block.

import {
  to = aws_s3_bucket.legacy
  id = "sf-legacy-reports-bucket"     # the ID format depends on the resource type
}

resource "aws_s3_bucket" "legacy" {
  bucket = "sf-legacy-reports-bucket"
}
  • Imports happen during plan and apply, so you see them in the plan before anything is recorded: Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.
  • The id is whatever the provider uses to find the object: a bucket name, an instance id such as i-0abc..., a security group id. Each resource page in the provider documentation has an Import section with the format.
  • Since Terraform 1.7, an import block can use for_each to import many objects at once.
  • After a successful import you can delete the import block, or keep it as a record. It has no effect once the resource is in state.

Generating the configuration

Writing a matching resource block yourself can be slow. Terraform can write a first draft for you:

# main.tf has only the import block, no resource block yet
terraform plan -generate-config-out=generated.tf

Terraform writes generated.tf with a resource block filled in from the real object. Review and tidy it, then apply. The file must not already exist.

2

The terraform import command

The older CLI way, and how it differs.

terraform import aws_s3_bucket.legacy sf-legacy-reports-bucket
import blockterraform import command
Reviewed in a plan firstYesNo, it writes to state immediately
Imports many at onceYes, with for_eachOne resource per command
Can generate configurationYes, with -generate-config-outNo
Works in HCP Terraform VCS runsYes, it is part of the codeNo, it needs a local CLI run
Needs the resource block to exist firstNo (it can be generated)Yes
Watch out

Import records an object in state; it does not check that your resource block matches it. Always run a plan after importing. Any difference shows as a change, and applying it would alter the real resource to match your code.

3

Inspecting state and verbose logging

terraform state subcommands, and TF_LOG.

terraform state

CommandWhat it does
terraform state listLists every address in state. Accepts a filter: terraform state list module.web
terraform state show ADDRESSShows all attributes of one resource
terraform state mv SOURCE DESTMoves a resource to a new address in state (the moved block is the code-based way)
terraform state rm ADDRESSRemoves a resource from state; the real object is left alone (the removed block is the code-based way)
terraform state pullPrints the current state as JSON, from any backend
terraform state pushOverwrites the remote state with a local file. Rarely needed and risky.
terraform state replace-providerChanges the provider source recorded for resources

The commands that change state (mv, rm, push) write a backup first when the state is local.

Verbose logging with TF_LOG

When something fails and the error is not clear, turn on detailed logs with the TF_LOG environment variable.

export TF_LOG=DEBUG              # TRACE, DEBUG, INFO, WARN or ERROR (TRACE is the most detailed)
export TF_LOG_PATH=./terraform.log   # write the log to a file instead of the screen
terraform plan

export TF_LOG_CORE=WARN          # set Terraform's own log level separately
export TF_LOG_PROVIDER=TRACE     # ...from the providers' log level

unset TF_LOG TF_LOG_PATH TF_LOG_CORE TF_LOG_PROVIDER   # turn logging off
  • TF_LOG_PATH only takes effect when a log level is set.
  • If Terraform crashes, it writes a crash.log file with the details to report.
Watch out

TRACE and DEBUG logs can contain request details, tokens and secrets. Do not share them or leave them in CI logs without checking them first.

Lab: adopt a manually created bucket

Import with generated configuration, inspect state, and read a debug log.

1. Create a bucket manually

NAME="tf2-m7-legacy-$(date +%s)"
aws s3api create-bucket --bucket "$NAME" --region us-east-1
echo "$NAME"

2. Import it with a generated configuration

Create a folder tf2-lab-m7 with this file, using the bucket name from step 1:

tf2-lab-m7/main.tf

terraform {
  required_version = ">= 1.12.0"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}

provider "aws" {
  region = "us-east-1"
}

import {
  to = aws_s3_bucket.legacy
  id = "tf2-m7-legacy-1234567890"   # your bucket name
}
cd tf2-lab-m7
terraform init
terraform plan -generate-config-out=generated.tf
cat generated.tf           # a full aws_s3_bucket block, written for you
terraform plan             # Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.
terraform apply

If the second plan reports an error about an argument in generated.tf, remove that argument from the file and plan again. Generated configuration is a draft and sometimes needs tidying.

3. Inspect state

terraform state list
terraform state show aws_s3_bucket.legacy
terraform state pull | head -20

4. Read a debug log

TF_LOG=DEBUG TF_LOG_PATH=./debug.log terraform plan
grep -c "DEBUG" debug.log
grep -i "http request" debug.log | head -3    # the provider's calls to AWS
rm debug.log

Clean up

Add force_destroy = true to the bucket in generated.tf, apply, then destroy. The bucket is now managed by Terraform, so terraform destroy removes it.

terraform apply
terraform destroy
Check your work
  • The plan after generating showed 1 to import and nothing else
  • terraform state list showed aws_s3_bucket.legacy
  • debug.log contained the provider's requests to AWS
