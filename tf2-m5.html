Remote State and Locking

Move state off your laptop into a shared, locked, encrypted backend so a team can work on the same infrastructure safely.

Before you begin

In Course 1 all state was in a local terraform.tfstate file. That works for one person on one computer. As soon as a second person or a pipeline runs the same configuration, state must live somewhere shared, and only one run must be able to change it at a time.

1

Why remote state

Shared, backed up, encrypted and locked.

A remote backend stores state in a shared place, such as an S3 bucket or HCP Terraform.

Problem with local stateHow a remote backend helps
Only the person with the file can run TerraformEveryone and every pipeline reads the same state
Laptop lost, file deletedState is stored centrally, and S3 versioning keeps old copies
Secrets sit on a laptop diskState is encrypted at rest and access is controlled with IAM
Two people apply at once and overwrite each otherState locking lets only one run write at a time

Common backends include s3, azurerm, gcs, consul, kubernetes and pg. HCP Terraform is set up with a cloud block instead of a backend block (Module 8).

2

State locking

How locking works, and what to do when a lock is left behind.

When a command that can write state starts (plan, apply, destroy, import and so on), Terraform takes a lock on the state. A second run that tries to take the lock fails with an error that shows who holds it. Locking happens automatically for backends that support it.

What a second person sees

Error: Error acquiring the state lock
  Lock Info:
    ID:        6f1c2d3e-...
    Path:      sf-tf-state/course2/terraform.tfstate
    Operation: OperationTypeApply
    Who:       priya@laptop
OptionUse
-lock-timeout=5mWait up to 5 minutes for the lock instead of failing at once
-lock=falseRun without a lock. Dangerous; avoid it.
terraform force-unlock LOCK_IDRemove a lock left behind by a run that crashed. Only use it when you are sure no run is still going.
Exam tip

Not every backend supports locking. The S3 backend does, with use_lockfile = true (Terraform 1.10 and later). Older setups used a DynamoDB table for locking; that option is now deprecated.

3

The backend block

Configure the S3 backend, and move existing state into it.

terraform {
  backend "s3" {
    bucket       = "sf-tf-state-123456789012"
    key          = "course2/lab/terraform.tfstate"   # path of the state file in the bucket
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true                              # S3-native locking
  }
}
  • A backend block cannot use variables, locals or data sources. Values must be written literally, or supplied at init time.
  • Only one backend block is allowed per configuration.
  • After adding or changing the backend block, run terraform init again.

Partial configuration

You can leave settings out of the block and pass them when you initialise. This keeps account-specific values out of the code.

# backend "s3" {}   in the code, and:
terraform init -backend-config="bucket=sf-tf-state-123456789012" \
               -backend-config="key=course2/lab/terraform.tfstate" \
               -backend-config="region=us-east-1"

# or put the settings in a file:
terraform init -backend-config=backend.hcl

Moving state between backends

CommandDoes
terraform init -migrate-stateCopies existing state to the new backend (Terraform asks first)
terraform init -reconfigureUses the new backend settings and ignores the old state (no copy)

Reading another configuration's state

The terraform_remote_state data source reads the outputs of another configuration's state, for example a network built by another team.

data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "sf-tf-state-123456789012"
    key    = "network/terraform.tfstate"
    region = "us-east-1"
  }
}

# data.terraform_remote_state.network.outputs.vpc_id
Watch out

To read outputs with terraform_remote_state, you need read access to the whole state file, which can include secrets. Where possible, share values another way, such as through data sources or HCP Terraform outputs.

4

Lab: move local state to S3

Create a state bucket, migrate state into it, and see a lock stop a second run.

1. Create the state bucket

The state bucket is created outside the configuration that uses it, so it is never destroyed with that configuration. Use the AWS CLI:

ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
BUCKET="tf2-state-$ACCOUNT"
aws s3api create-bucket --bucket "$BUCKET" --region us-east-1
aws s3api put-bucket-versioning --bucket "$BUCKET" --versioning-configuration Status=Enabled
echo "$BUCKET"     # note this name

2. Start with local state

tf2-lab-m5/main.tf

terraform {
  required_version = ">= 1.12.0"
  required_providers {
    aws    = { source = "hashicorp/aws", version = "~> 6.0" }
    random = { source = "hashicorp/random", version = "~> 3.6" }
  }
}

provider "aws" {
  region = "us-east-1"
  default_tags { tags = { Project = "tf-course-2", Lab = "m5" } }
}

resource "random_pet" "name" {}

resource "aws_s3_bucket" "app" {
  bucket        = "tf2-m5-app-${random_pet.name.id}"
  force_destroy = true
}

output "app_bucket" {
  value = aws_s3_bucket.app.bucket
}
cd tf2-lab-m5
terraform init
terraform apply
ls terraform.tfstate     # local state exists

3. Add the backend and migrate

Add this block inside the existing terraform { } block, using your bucket name:

Add to tf2-lab-m5/main.tf

  backend "s3" {
    bucket       = "tf2-state-123456789012"   # your bucket
    key          = "course2/m5/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
terraform init -migrate-state        # answer yes to copy the state
terraform plan                       # no changes: the state moved, not the resources
aws s3 ls "s3://$BUCKET/course2/m5/"

Terraform now reads and writes state in S3. The local terraform.tfstate file is no longer used and can be deleted.

4. See the lock

Open a second terminal in the same folder. In the first, run terraform apply and leave it waiting at the yes prompt. In the second, run terraform plan. It fails with Error acquiring the state lock. Answer no in the first terminal, and the second can run again.

5. Clean up

terraform destroy
aws s3 rm "s3://$BUCKET" --recursive
aws s3api delete-objects --bucket "$BUCKET" --delete "$(aws s3api list-object-versions --bucket "$BUCKET" --query '{Objects: Versions[].{Key:Key,VersionId:VersionId}}' --output json)"
aws s3api delete-bucket --bucket "$BUCKET"

If the last command reports that the bucket is not empty, run the delete-objects line again with DeleteMarkers in place of Versions. Keep the bucket instead if you want to reuse it for the Course 2 graded lab.

Check your work
  • terraform plan after the migration showed no changes
  • The state file appeared under course2/m5/ in the bucket
  • The second terminal got the state lock error

Module recap. Remote backends store state centrally, encrypted and backed up. Locking lets only one run write at a time; the S3 backend locks with use_lockfile. Backend blocks cannot use variables, so use -backend-config, and move state with init -migrate-state.
