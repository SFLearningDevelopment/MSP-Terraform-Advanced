Before you begin

In Course 1 you found a password in plain text inside terraform.tfstate, even though the output hid it. This module covers the ways to handle secrets properly: marking values sensitive, getting secrets from Vault, and the newer ephemeral values and write-only arguments that are never stored at all. The last two were added in version 004 of the exam.

1

Sensitive values and where secrets leak

What sensitive = true protects, and what it does not.

A secret can leak from a Terraform project in five places: the .tf files, .tfvars files, command output, logs and the state file.

WhereHow to protect it
.tf and .tfvars files in GitNever write secrets in them. Pass them through TF_VAR_ environment variables, a secrets manager or Vault.
Plan and apply outputMark variables and outputs sensitive = true. Terraform then shows (sensitive value).
Logs from CI pipelinesSame as above; also avoid TF_LOG=TRACE in shared pipelines.
The state fileStore state in an encrypted remote backend with restricted access (Module 5). Use ephemeral values and write-only arguments so the secret is never written.
variable "db_password" {
  type      = string
  sensitive = true
}

output "db_endpoint" {
  value = aws_db_instance.main.endpoint
}

output "db_password" {
  value     = var.db_password
  sensitive = true    # required: an output that uses a sensitive value must say so
}
  • Sensitivity spreads: any expression built from a sensitive value is also sensitive.
  • The sensitive() function marks a value as sensitive; nonsensitive() removes the mark when you are sure it is safe.
  • Many provider attributes are already marked sensitive, such as a database password.
Watch out

sensitive = true only hides values on screen. The value is still stored in plain text in the state and in saved plan files.

2

Secrets from Vault

Read secrets at run time instead of storing them in files.

HashiCorp Vault stores secrets centrally, controls who can read them and records every read. The hashicorp/vault provider lets Terraform read a secret when it runs, so the secret never sits in your files or in Git.

provider "vault" {
  address = "http://127.0.0.1:8200"    # usually set with VAULT_ADDR instead
  # token comes from the VAULT_TOKEN environment variable
}

data "vault_kv_secret_v2" "db" {
  mount = "secret"
  name  = "app/db"
}

# data.vault_kv_secret_v2.db.data["password"]

This keeps the secret out of your files, but a data source result is saved in state. To keep it out of state as well, read it as an ephemeral resource instead (next section).

Vault can also issue dynamic secrets: short-lived AWS credentials or database users created on request and removed when they expire. A leaked dynamic secret is only useful for a short time.

3

Ephemeral values and write-only arguments

Values that are used during a run and never stored.

Terraform 1.10 and 1.11 added ways to use a secret without saving it in the plan or state.

FeatureWhat it is
ephemeral resource blockReads or creates a value for the length of one run, such as a secret from Vault or AWS Secrets Manager. Its values are never stored in the plan or state. Referenced as ephemeral.<type>.<name>.
ephemeral = true on a variableThe variable's value is available during the run but not stored.
ephemeral = true on an outputAllowed in child modules, to pass an ephemeral value up to the caller.
Write-only argumentA resource argument that accepts a value, usually ephemeral, sends it to the provider and never stores it. Their names end in _wo, such as password_wo.
# Read the secret for this run only
ephemeral "vault_kv_secret_v2" "db" {
  mount = "secret"
  name  = "app/db"
}

resource "aws_db_instance" "main" {
  identifier          = "app-db"
  engine              = "postgres"
  instance_class      = "db.t4g.micro"
  allocated_storage   = 20
  username            = "app"
  skip_final_snapshot = true

  # Write-only: sent to AWS, never saved in state
  password_wo         = ephemeral.vault_kv_secret_v2.db.data["password"]
  password_wo_version = 1    # increase this number to send a new password
}
  • Because Terraform does not store a write-only value, it cannot tell when it changes. Each write-only argument has a matching _version argument; change it to make Terraform send the value again.
  • Ephemeral values can only be used where ephemeral values are allowed: other ephemeral blocks, write-only arguments, provider configuration, locals and ephemeral variables and outputs. Using one in a normal argument is an error.
Exam tip

A data source reads a value and stores it in state. An ephemeral resource reads a value and never stores it. A write-only argument accepts a value and never stores it.

4

Lab: a secret that never reaches state

Run a local Vault server, read a secret ephemerally, and store it through a write-only argument.

1. Start a Vault dev server

Install Vault the same way you installed Terraform (brew install hashicorp/tap/vault or sudo apt install vault). In one terminal, start a dev server. It keeps data in memory only and is for learning, never for real secrets.

vault server -dev -dev-root-token-id="root"

In a second terminal:

export VAULT_ADDR="http://127.0.0.1:8200"
export VAULT_TOKEN="root"
vault kv put secret/app/db password="Lab-Only-Pa55word"
vault kv get secret/app/db

2. The configuration

Instead of a database, which takes a long time to create, this lab stores the password in AWS Secrets Manager through its write-only argument secret_string_wo.

tf2-lab-m3/main.tf

terraform {
  required_version = ">= 1.12.0"
  required_providers {
    aws    = { source = "hashicorp/aws", version = "~> 6.0" }
    vault  = { source = "hashicorp/vault", version = ">= 4.7" }
    random = { source = "hashicorp/random", version = "~> 3.6" }
  }
}

provider "aws" {
  region = "us-east-1"
  default_tags { tags = { Project = "tf-course-2", Lab = "m3" } }
}

provider "vault" {}   # uses VAULT_ADDR and VAULT_TOKEN

ephemeral "vault_kv_secret_v2" "db" {
  mount = "secret"
  name  = "app/db"
}

resource "random_pet" "name" {}

resource "aws_secretsmanager_secret" "db" {
  name                    = "tf2-m3-db-${random_pet.name.id}"
  recovery_window_in_days = 0   # delete at once on destroy (lab only)
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id                = aws_secretsmanager_secret.db.id
  secret_string_wo         = ephemeral.vault_kv_secret_v2.db.data["password"]
  secret_string_wo_version = 1
}

output "secret_name" {
  value = aws_secretsmanager_secret.db.name
}
cd tf2-lab-m3
terraform init
terraform apply
grep -c "Lab-Only-Pa55word" terraform.tfstate     # 0: the password is not in state
aws secretsmanager get-secret-value --secret-id "$(terraform output -raw secret_name)" --query SecretString

3. Change the secret

Run vault kv put secret/app/db password="Lab-Only-New-Pa55", then terraform plan. Terraform reports no changes, because it never stored the old value to compare with. Change secret_string_wo_version to 2 and plan again: now it sends the new value. Apply, check it with the aws command above, then clean up.

terraform destroy
# stop the Vault dev server with Ctrl+C in the first terminal
Check your work
  • grep -c returned 0 for the state file
  • AWS Secrets Manager returned the password from Vault
  • The new password was only sent after you changed secret_string_wo_version
